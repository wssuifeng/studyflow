## 2. SQLite 根因与修复

### 根因证据

在 Windows 11、Python 3.13.0、SQLite 3.45.3、SQLAlchemy 2 的真实 StudyFlow schema 下，整课 ORM `RETURNING` 连续写入约 187—281 条时稳定复现：

```text
sqlite3.OperationalError: unable to open database file
SQLite error code: SQLITE_CANTOPEN (14)
```

进一步对照确认：

- 同一 schema 使用 raw sqlite driver 连续写入 500 条通过；
- SQLAlchemy 的普通 `exec_driver_sql` 路径连续写入 500 条通过；
- ORM flush 使用默认 `temp_store=FILE` 时失败；
- 在同一连接设置 `PRAGMA temp_store=MEMORY` 后 500 条通过；
- 失败事务完整回滚，数据库中未留下半批提交；
- 不是磁盘空间不足、业务唯一约束或 WAL 配置问题。

### 实施

在 `packages/core/src/studyflow/infrastructure/persistence/database.py` 增加 SQLite 连接初始化：

```sql
PRAGMA temp_store=MEMORY
```

该设置只作用于 SQLite 连接，MySQL 路径不执行；`init_db(engine)` 也会为测试或外部调用者直接创建的 Engine 配置该 pragma。

### 验证

```powershell
cd <repo-root>\packages\core
.\.venv\Scripts\python.exe -m pytest tests/test_optimization.py::test_file_sqlite_keeps_temp_store_in_memory tests/test_optimization.py::test_whole_course_500_boundary_and_501_no_registration -q
.\.venv\Scripts\python.exe -m pytest tests/test_optimization.py::test_hundred_courses_two_thousand_answers_queue_projection -q
.\.venv\Scripts\python.exe -m pytest -q
```

结果：专项 2+1 项通过；Core 全量测试通过。原 500/2000 两个 `CANTOPEN` 失败不再复现。

## 3. 课程清理共享 Markdown 保护

`CourseService` 的清理库存和删除流程现在支持内部按课程 ID 计算待删集合，并区分：

- `document_paths`：待清理课程引用过的路径；
- `deletable_document_paths`：删除集合之外没有剩余 Lesson 引用的路径；
- `protected_document_paths`：仍被其他课程 Lesson 引用的共享路径。

物理 Markdown 文件与 `Document` 记录只对 `deletable_document_paths` 执行删除。新增测试覆盖：课程 A、B 共用同一 Markdown，清理 A 后课程 B、文件和 `Document` 记录仍保留。

验证：

```powershell

```

结果：5/5 通过。
