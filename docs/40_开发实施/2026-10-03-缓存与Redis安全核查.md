# 缓存与Redis安全核查 · 2026-10-03

## 结论先行

用户报告Codex曾拦截开放范围过大的Redis操作，本轮要求仅为StudyFlow专项开放。**已核对当前运行态并补充项目操作约束；尚未取得被拦截命令，未对系统Redis/Memurai执行运行态修复。** 不能把“当前未见全网监听”写成“历史问题已定位并修复”。

StudyFlow当前默认SQLite、Vue本机偏好及Python Engine，不需要为主题或模拟批改新建Redis。现有源码及所查依赖没有Redis接入证据。最小范围的处理是不启动/开放一个不需要的服务，不更改共享服务或全局安全设置。

## 已完成的只读发现

| 安装CLI健康 | 1.7.0工作区doctor返回healthy=true、工作区和数据库可写；数据库为应用管理的SQLite。工作区绝对路径/请求留在私有记录，不公开 |

| 精确配置读取 | 只向本机服务发送`CONFIG GET bind`、`CONFIG GET protected-mode`、`CONFIG GET port`；分别返回`127.0.0.1`、`yes`、`6379`。没有读取密码/ACL密码散列/数据键，没有发送修改命令 |

上述Memurai服务没有证据归属于StudyFlow。本轮未停止/重启它，也未改配置、服务启动方式、防火墙、ACL、系统PATH或Codex全局权限。

**残余边界：** loopback和protected mode不是命令权限审计。此次无凭据即可读取这三项CONFIG，至少说明这些读取可用；不据此声称认证/ACL已满足最小权限，更不擅自修改可能供其他项目使用的实例。

## 本轮已落实的预防约束

1. 在StudyFlow AGENTS加入缓存/服务范围纪律；主题专项也明确禁止引入或放开Redis来解决样式、测试或权限问题。
2. 本软件的缓存/构建/测试只使用已声明的项目专属目录；外观偏好使用本机应用命名空间，不放开全局缓存或目录权限。
3. 不使用`bind 0.0.0.0`、关闭protected mode、给default用户全命令全键/全频道权限、删除认证或全局修改防火墙作为排障捷径。
4. 不因请求被拦截而换一种表达重试同一危险命令；先还原需要的最小操作和边界。
5. 若以后确有Redis业务依赖，先核对实例归属及版本，再做应用专用用户/键与频道前缀/命令白名单和loopback限制；独立DB编号不代替权限隔离。密钥不写源码、公开提示词或日志。

这些是操作约束纠偏，**不是已修改Redis运行配置的证明**。

## 尚待用户提供的最小信息

被拦截的命令或提示截图（隐去密码/token），最好保留命令中的程序、目标地址/端口及拟修改项。随后才可判断它是临时测试服务、Memurai、其他项目实例，还是权限描述的歧义，并仅修正StudyFlow相关操作。当前没有足够依据对其他系统服务下手。
